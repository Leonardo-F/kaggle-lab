## 3. 目标结构测试：是否存在可利用的共享结构

对 1,000 道正式题做的检验：

| 检验 | 结果 | 含义 |
| --- | --- | --- |
| 目标之间是否存在 1 条指令的直接关系 | 练习集各家族 0–0.6%（仅 `tiny` 家族 78.6%） | 目标不是彼此的中间值 |
| 目标差集是否近似小分母有理比 | 前 5 题 0 命中 | 不存在 `V·k` 型共享乘子 |
| 目标两两 gcd 是否 > 2^20 | 前 6 题 0 命中 | 不存在共享大因子 |
| 目标是否共享 > 1000 的素因子 | 抽样 200 题中 3–4% | 乘法共享很少 |
| 相邻目标间距 ≤ 2^12 的比例 | 抽样 80 题中 5% | 近邻簇只占少量目标 |
| 所有差值的 gcd | 前 40 题均 < 2^8 | 无隐藏模数结构 |

即：正式题的目标基本是"随机大整数"，需要逐目标构造。公开前沿的 1.8 倍优势**不是**靠发现某种解析式，而是靠更强的联合搜索（在目标之间共享中间值、并反复局部改写）。

### 程序结构剖析（只读学习，不用于提交）

以 `scored_0001`（32 个 47–50 位目标，frontier 223 步、我们 432 步）为例，实际指令序列呈现出清晰的三层"阶梯"：

1. **小块池**（~13 位，约 30 个）：`4417 = 7·631`、`4137 = 591·7`、`5306 = 4417 + 889`、`6252 = 1563·4` —— 全是起始值的乘、加、减、除组合；
2. **中层**（~24 位，约 150 个）：`23436602 = 5306·4417`、`17114769 = 4137²`、`9673230 = 4417·2190`、`12751490 = 9672294 + 3079196`；
3. **目标层**：目标由中层值再做一两次加/减/乘得到，例如 `14030257 = 26781747 − 12751490`、`9407904 = 23438161 − 14030257`。

关键点：中层值**跨目标共享**（每个目标的祖先约 47 个节点，而整题只有 223 步），因此 32 个目标只花 223 步。我们的求解器为每个目标单独铺 radix 链，所以是 432 步。

### 下一步实现方向

把"逐目标 radix"换成"**共享小块池 + 中层积/差格 + 目标层组合**"，并用贪心/退火优化池的组成（这正是 DAG-LNS 的 destroy-repair 循环）：

1. 小块池：起始值的 1–2 步组合，筛出 ~30–60 个；
2. 中层池：小块两两乘积（~20–26 位）及其和/差，按"能服务多少目标"贪心选择；
3. 目标层：对每个目标 `t`，在池中找 `t = A ± B`、`t = A·B ± c`，取增量最小者；找不到再降级到 radix；
4. 迭代：删除利用率低的中层节点，重新修补受影响目标（LNS 的 destroy-repair）。

预期：40–49 档从 11.64 降到 5–6 可省约 4 万步，全量有望进入 18–20 万区间。

## 4. 我们尝试的新算法与实测结果

当时实现了值图改写器（见[历史实验代码](https://github.com/Leonardo-F/kaggle-lab/blob/378f74bda50672bc298a636a9a0032c92fd3bcf5/competitions/santa-2026/legacy/graph_polisher.py)）。做法：把一份合法程序的**所有产出值**都当作可用操作数（旧求解器只能用当前 48 个活跃寄存器），再逐目标寻找更短的重新推导，循环到不动点，最后重新分配寄存器；每一步都用 旧版回放器 校验，只保留更短的程序。

包含四个改写族：

1. 单指令重推：`t = a ± b`、`a*b`、`a/b`，`a,b` 取任意已产出值；
2. 双指令重推：`t = (a op b) op c`（中间值落图后可被其它目标复用）；
3. 锚点重推：`t = u + (t-u)`，`u` 为图上邻近值，偏移量递归构造；
4. 隐藏锚点发现：对 `u = a op b` 统计有多少目标满足 `t-u` 已在图上，命中 ≥2 就建 `u` 并让这些目标各用 1 条指令。

实测（正式集 1,000 题，逐版本迭代打磨）：

| 数据 | 改写前 | 改写后 | 变化 |
| --- | ---: | ---: | ---: |
| 练习集 200 题（早期单步版本） | 55,614 | 55,544 | −0.13% |
| 正式集 1,000 题（严格单步版本，不动点） | 270,450 | 270,450 | 0 |
| 正式集 1,000 题（修正锚点接受条件 + 双指令改写，迭代三轮） | 270,450 | 269,706 | −0.28% |
| 正式集 1,000 题（多轮打磨 + 逐题取最短合并） | 270,450 | 269,611 | −0.31% |
| 正式集 1,000 题（锚点变体搜索 + 两轮合并） | 270,450 | 269,474 | −0.36% |
| 正式集 1,000 题（追加变体 6/7、倍增变体 5，再合并） | 270,450 | 269,413 | −0.38% |
| 正式集 1,000 题（有理链改写 `(a·p+c)/q` + 合并） | 270,450 | **269,369** | **−0.40%** |

最终版本：279 题变短、721 题持平、0 题变长；最长程序 525 步（限制 4,096）；独立回放 1,000 题全部通过。改进集中在有链式/近邻结构的题目。严格单步版本之所以是 0，是因为它只接受"立即变短"的改写；放宽为"先接受锚点改写、再按整题长度择优"后，可以跨过局部平台（这正是公开方案里"每题目上万轮打磨"的作用）。

归档：`elf-calculator-score-269385.csv`（提交 `64db409`）。

另外验证过两条纯求解路线，均未超过现有提交：

* 自顶向下的成本传播规划器（按 `(位宽, 值)` 排序做一次代价传播，再按最小边际成本物化目标）：在练习集抽样上多数题目给不出不劣于参考的程序（预算内不可达或更长），未用于提交。

### 为什么停在 0.38%

按可达值增长模型：从 4 个 10 位起始值出发，5 条指令可达约 2×10⁹ 个不同值，而随机 47 位目标空间是 1.4×10¹⁴——**随机 47 位目标的下限约 7–8 条指令**（我们 14.5）。要逼近这个下限，必须在上亿级表达式空间里做联合搜索（公开方案自述"每题目两万轮"），而局部改写只能调整已有分解，无法生成全新的分解结构。

## 5. 结论与建议

1. 现有程序在"严格单点改写"下已局部饱和（0 收益），放宽为允许跨平台、多轮变体搜索、有理链改写后再逐题取最短仍有 0.39% 收益；但公开前沿的差距需要**联合搜索**（同时决定建哪些共享中间值、以及所有目标的分解），而不是继续加改写规则。
2. notebook 自述的做法（逐题回放取最短 + 每题目约 20,000 轮 value-graph 打磨）与我们测到的差距量级一致：那是大量算力换来的逐题最优并集，单靠一次性构造难以匹配。
3. 若要继续冲榜，建议按以下顺序投入：先实现"全局共享中间值搜索"（集合覆盖式贪心 + 模拟退火，目标函数为整题指令数），再对每题做多轮局部打磨；预计需要 2–3 天开发与大量 CPU 时间，且收益不确定。

### 实现进展：`product_pass`（2026-11-24）

当时在值图改写器中加入 `product_pass`：对每个目标尝试 `t = a·round(t/a) + c`（`a` 取图上最便宜的值，`c` 为残差），并按整题长度择优。**单独启用时实测 0 收益**——因为 `round(t/a)` 与 `c` 在当前图里都不存在，`ensure` 会按 radix 现造，成本与现有分解持平。

这验证了前面的判断：**收益不来自"乘积形式"本身，而来自共享池**——frontier 的 `M1`、`M2`、`c` 都由同一个约 200 节点的中层池拼出，跨目标复用。因此下一步必须实现"池的选择"（集合覆盖/LNS），而不是再加一种单目标分解形式：

1. 候选池 `C`：`L1`（起始值 1 步组合，~30 个）两两乘积（~20–26 位，~800 个），再与 `L1` 求和/差（~20–26 位）；
2. 解释枚举：对每个目标 `t`，对每个 `a ∈ C` 取 `M2 = round(t/a)`、`c = t − a·M2`；若 `M2`、`c` 也能在 `C` 中找到（或由 `C` 中两元素一步得到），则该目标可被 `a`、`M2`、`c` 三个池值解释（增量 2 步）；
3. 贪心集合覆盖：统计每个候选池值服务多少目标，按 (服务数 / 构建成本) 从高到低选入池，直到边际收益为负；
4. 物化池与目标，交给现有 `emit` 调度；再用 LNS（删除低利用率池值、重修补受影响目标）迭代。

预计这一步能把 40–49 档从 11.64 压到 5–7，全量进入 18–20 万。

### 已验证的结构配方（2026-11-24）

用"小块池"直接检验 frontier 的构造形式 `t = M1·M2 − (p − q)`（M1 取小块乘积、M2 取 `round(t/M1)`、残差用池内两值之差表示）：

| 题 | 池大小（块+乘积+和差） | 能被该形式解释的目标 |
| --- | ---: | ---: |
| scored_0001 | 901 | 31 / 32（其中 29 个只需 3 步：乘、加、减） |
| scored_0006 | 312 | 32 / 32（3 个 1 步、14 个 2 步、15 个 3 步） |

**结论**：形式本身成立且覆盖极高，剩余成本全在"池要多大、怎么选"。逐目标现造 `M2`（约 24 位，radix 成本 4–5）只能把 11.6 降到 ~9–10；要做到 frontier 的 5.2，必须让 `M1`、`M2`、`c` 三者都落在同一个约 150 节点的池里（跨目标复用）。

因此待办收敛为一件：**池选择**（贪心集合覆盖 + LNS destroy-repair）。本次尝试的 `pool_solver.py` 原型因"要求 M2 也在池内"导致覆盖率不足、且池的选择还没实现，已删除，避免留下半成品代码；配方与实测覆盖率记录在此。

## 6. 当前口径：V10 之后的差距（2026-11-27）

前五节是 2026-11-23 至 11-24 的调研与实验历史，保留原样。V9 合入后，本地独立求解正式 1,000 题为 **175,604 步**（V8 194,444 → V9 Stage 1 182,205 → Stage 2 175,604）。V10 Full 把同一批正式题压到 **164,306 步**（1,000/1,000 独立回放合法、最长 349；V9 175,604 → V10 Stage 3 165,110 → Full 164,306），详见 [v10.json](reports/v10.json)。这是**本地验证的指令总数，不是 Kaggle 榜单成绩**，我们未做 Kaggle 提交。

对照公开前沿：该 notebook 自报榜单分数 **128,513**，性质是社区"逐题最短程序"的并集；我们回放其公开数据集得到 128,507（见 §3b）。按同一批官方题对比：

- 自研独立 V9 175,604 / 社区并集 128,513 ≈ **1.37 倍**；V10 Full 164,306 / 128,513 ≈ **1.28 倍**（对回放口径 128,507 同样约 1.28 倍）；
- 历史参照：V1 的 250,642 约为 1.95 倍、值图改写器时代的 270,450 约为 2.10 倍。差距缩小来自本仓库 V2–V9 的自研算法迭代，不是复制前沿程序。

必须区分三个口径：
